# 휴대폰 직접 페어링 기반 감지 전환 계획

작성: 2026-10-20. **B 연결 게이트 및 C 화면 핵심 실물 시험 통과. D 광고 스캔/설정/UI 제거본을 업로드·읽기 검증했고 PC 0.3.0도 동일 경로에 적용했다. D 부팅·자동 연결·사용량/ACK·PC 상태 표시와 짧은 안정성 확인을 통과했다. 예약 실물 시험은 사용자 사정으로 보류했고 PC 완전 종료 등 남은 E 항목은 미검증이다.** 최신 상태는 18절을 따르며 12~17절은 이미지별 진행 이력이다.

## 1. 확정한 요구와 범위

- 기존 휴대폰 BLE 광고 검색·이름/별칭/광고 주소 일치 방식은 폐기한다. 대체 감지 수단이나 자동 fallback으로 남기지 않는다.
- 보드와 Fold7을 직접 BLE 페어링하고, 등록한 휴대폰의 **인증된 실제 연결 상태**로 화면을 제어한다. 저장된 페어링 정보만으로 재실 판정하지 않는다.
- 휴대폰 추가 앱, PC를 통한 휴대폰 감지, Wi-Fi, 추가 태그를 전제로 삼지 않는다.
- PC는 기존처럼 사용량을 보드에 전달할 수 있어야 한다. PC와 폰을 함께 페어링·연결할 수 있고, PC가 꺼지거나 연결이 끊겨도 폰 감지와 화면 제어는 보드에서 계속되어야 한다.
- 1차 지원 범위는 기존 PC 1대 + 감지 대상 휴대폰 1대다. 여러 휴대폰의 OR/AND 감지는 범위에 넣지 않는다.
- 계획을 작성한 이전 세션에서는 계획과 인수인계만 작성했다. 실제 소스 전환·업로드·휴대폰 페어링은 후속 세션에서 진행하며, 현재 결과는 12절에 기록한다.

## 2. 출발점과 가장 먼저 확인할 조건

현재 펌웨어는 `CONFIG_BT_NIMBLE_MAX_BONDS=1`, `CONFIG_BT_NIMBLE_MAX_CONNECTIONS=1`이다. `ble_transport.cpp`는 연결 핸들·인증·알림 구독·수신 재조립·송신 epoch를 하나씩만 관리한다. 숫자만 2로 바꾸면 새 연결이 기존 PC 상태를 덮어쓸 수 있다.

ESP32-S3/NimBLE의 복수 BLE 연결 지원은 확인했다. 그러나 **일반 GATT 장치를 Fold7의 기본 Bluetooth 설정에서 페어링하면, 앱 없이 잠금 중 연결과 복귀 후 자동 재연결까지 유지되는지는 미확인**이다. 하드웨어의 멀티 연결 지원과 폰 OS의 연결 동작은 별개다.

첫 실물 검증에서 다음 네 항목을 확인한다.

1. 휴대폰 기본 Bluetooth 설정에서 보드 검색·번호 비교·본딩이 된다.
2. 폰이 이름 광고를 하지 않아도, 본딩된 폰의 인증된 연결을 보드에서 구분한다.
3. 화면 잠금 중에도 연결이 유지된다.
4. 범위 이탈 후 복귀하면 휴대폰을 조작하지 않아도 다시 연결된다.

이 네 항목 중 하나라도 실패하면 전체 UI 통합·감지 활성화 전에 원인을 확인한다. 단순히 본딩이 성공한 것만으로 다음 검증을 통과한 것으로 취급하지 않는다. 폰이 광고하지 않는 상태에서 보드가 저장 주소로 무조건 접속할 수 있다고 가정하지 않는다.

일반 GATT로 OS 자동 연결이 안 되는 경우, 필요한 표준 BLE 프로파일이 있는지 별도로 검토한다. HID 등은 폰에 입력 장치로 나타나거나 키보드 동작에 영향을 줄 수 있으므로 몰래 추가하지 않는다. 기존 조건에서 가능한 프로파일이 확인되지 않으면 검증 실패 사실과 선택지를 보고한다. 광고 스캔·앱·PC·Wi-Fi 방식으로 임의 전환하지 않는다.

## 3. 목표 연결 구조

| 구분 | PC 연결 | 휴대폰 연결 |
|---|---|---|
| 역할 | 사용량·설정·기존 heartbeat | 휴대폰 존재 확인 |
| 식별 | 저장된 PC 본딩 identity | LCD에서 등록한 폰 본딩 identity |
| 계정 데이터 접근 | 기존 인증·프로토콜 유지 | 사용량 쓰기·계정 알림 수신 불허 |
| 연결 유지 판정 | 기존 PC heartbeat와 ACK | BLE 링크 및 암호화·인증 상태 |
| 해제 영향 | 기존 사용량 삭제 정책 적용 | 60초 미연결 유예 시작 |
| 재연결 영향 | PC 스트림만 복구 | 폰 재실·화면 상태만 복구 |

- 보드는 우선 Peripheral 역할을 유지하고 PC·폰 두 Central의 연결을 따로 관리한다. 폰이 OS 기본 기능으로 이 역할을 수행하는지 2절에서 검증한다.
- 호스트의 최대 연결·본딩 수를 각각 2로 올린다. IDF 5.5.3의 실제 컨트롤러 activity/connection 설정도 확인해 광고와 두 연결이 공존하도록 맞춘다. 생성된 sdkconfig의 유효값까지 검사한다.
- 첫 연결 뒤에도 다른 슬롯을 위한 connectable advertising을 재개하고, 두 슬롯이 차면 정지하며, 슬롯이 비면 다시 시작한다. 이 광고는 폰이 보드를 찾기 위한 것이며 폐기하는 주변 폰 광고 스캔과는 다르다.
- Observer 기반 주변 스캐너와 목록 수집은 제거한다. **Windows가 Quotamon 보드를 찾는 기존 PC 검색 기능은 유지한다.**
- 연결 컨텍스트는 handle, generation/epoch, peer identity, 역할, 인증 상태, PC 전용 구독/수신 상태 등을 가진다. 이전 연결의 늦은 이벤트·송신·disconnect가 새 연결이나 다른 역할에 적용되지 않도록 한다.
- 역할 미확정 연결은 페어링 창의 대상과 본딩 결과로만 분류한다. 접속 순서·기기 이름·RSSI·임의 GATT 요청으로 PC 권한을 부여하지 않는다.

## 4. 본딩·등록과 권한

- LCD에 **PC 연결 등록**과 **휴대폰 등록**을 구분한다. 처음에는 두 등록 창을 동시에 열지 않아 번호 비교의 대상이 모호해지지 않게 한다. 이미 등록된 상대의 재연결은 허용한다.
- 기존 Secure Connections·MITM·6자리 번호 비교를 유지한다. 자동 승인이나 Just Works로 보안을 낮추지 않는다.
- 사용자 승인 후 인증·본딩 저장이 성공해야 휴대폰 등록을 확정한다. 취소·시간 초과·저장 실패는 등록 완료로 표시하지 않는다.
- 번호 비교 승인 이벤트에는 대상 역할·연결 handle·generation을 묶는다. 기존 전역 `connection`으로 다른 상대를 승인하지 않는다.
- identity와 역할의 대응은 보드 NVS에 저장한다. 현재 광고 주소나 표시 이름을 본딩 identity로 대신 쓰지 않는다. IRK/LTK 등 키는 NimBLE 저장소 내부에 두고 PC 설정·웹·로그에 내보내지 않는다.
- 기존 버전에서 유효한 본딩이 정확히 하나 있고 PC 전용 배포에서 이어진 경우에는 PC 역할로 보존하는 마이그레이션을 검증한다. 모호한 저장 상태는 임의 분류하지 않고 재등록 필요로 표시한다.
- 슬롯 부족 시 기존 PC 본딩을 자동 삭제하거나 교체하지 않는다. **휴대폰 삭제**는 폰 본딩/역할만, **PC 삭제**는 PC 본딩/역할만 지운다. `ble_store_clear()`를 일반 삭제 경로에서 쓰지 않는다.
- PC 송신·알림과 GATT 쓰기는 해당 PC 컨텍스트의 인증·권한을 검사한다. 폰이 PC용 characteristic에 쓰거나 구독해도 계정 데이터를 읽거나 변경할 수 없어야 한다.
- NVS 쓰기는 기존 원칙대로 DRAM 스택의 메인 작업으로 전달한다. NimBLE/LVGL 콜백에서 역할 저장을 직접 수행하지 않는다.

## 5. 감지 상태와 화면 정책

`disabled`, `unpaired`, `pairing`, `connected`, `disconnected_grace`, `absent`, `unavailable`를 구분하는 상태 모델을 둔다. 표시용 본딩 상태와 감지용 연결 상태도 분리한다.

| 상황 | 동작 |
|---|---|
| 등록한 폰의 인증된 연결 성립 | 즉시 재실. 예약 시간대가 아니고 별도 우선 조건이 없으면 화면 켜기 |
| 해당 폰의 연결 해제 | 화면을 유지하며 60초 유예 시작 |
| 유예 중 재연결 | 미감지 타이머 취소, 재실 복원 |
| 연결 해제 후 60초 경과 | 부재로 판정하여 화면 끄기 |
| 부팅·감지 활성화·대상 변경 | 초기 재연결을 위한 60초 유예 |
| 대상 없음·본딩 삭제 | 감지를 비활성화하고 재등록 안내. PC·예약 설정은 유지 |
| BLE 호스트 오류·재시작·복구 | 감지만을 이유로 화면을 끄지 않으며, 정상 복구 후 60초 유예 |
| PC 연결 해제·heartbeat 만료 | 사용량 삭제는 유지하되 폰 연결·감지 타이머·본딩에는 영향 없음 |
| 화면 끄기 예약 중 | 폰이 있어도 예약에 따라 끄기 |
| 꺼진 화면 터치 | 기존 밝기로 5분간 켜기. 유효한 터치 유예가 예약·부재보다 우선 |

- 60초는 **BLE가 연결 해제를 보고한 시점**부터다. 실제 이동 시점부터의 시간에는 링크 supervision timeout이 더해진다. 실제 협상된 연결 파라미터와 이탈→해제→꺼짐 시각을 기록해 지연을 확인한다.
- 폰에는 앱 heartbeat를 요구하지 않는다. 연결만 된 PC를 폰 재실로 간주하지 않는다.
- Bluetooth 끄기는 물리적 이탈과 동일하게 연결 해제로 처리한다. 타깃 휴대폰의 부재와 보드 자체 라디오 고장을 구분한다.
- `main.cpp`의 기존 35초 PC 무응답 처리, `clear()`, UI 페이지 전환이 폰의 상태나 등록 화면을 지우지 않도록 분리한다. PC 없이 사용량을 계속 표시하거나 최신 값으로 위장하지 않는다.

## 6. 설정·프로토콜·UI 전환

- D 확정 스키마: 보드가 `paired_presence_status`/`schema:2`/`capability:"paired-presence"`를 통지한다. `enabled`, `phone_bonded`, `phone_connected`, `presence_state`, `grace_remaining_seconds`, 표시용 `peer_id`/`name`을 포함한다. 감지 켜기/끄기와 타깃 관리는 LCD·보드 NVS가 소유하며 PC는 읽기 전용이다. PC 스냅샷 display에 휴대폰 감지 설정을 넣지 않는다.
- 타깃 본딩의 실제 identity/권한은 보드가 관리한다. PC가 전달한 peer ID 문자열만으로 미등록 기기에 권한을 부여하지 않는다. 이름은 표시 용도이고 감지 키가 아니다.
- 구형 `presence_address`·`presence_aliases`는 실행 로직에서 제거한다. 이전 광고 설정은 폐기하며 광고 설정만 있는 기기는 **휴대폰 미등록**으로 안내한다. 이미 B/C에서 명시적으로 등록한 폰 본딩과 로컬 `paired_on`은 보존하며, 구형 PC 필드로 새 감지를 끄거나 켜지 않는다. 이름은 표시 힌트로만 가져올 수 있다. 계정·예약·언어·밝기·PC 본딩은 보존한다.
- LCD에서 독립적으로 등록·번호 비교·삭제·감지 켜기/끄기가 가능해야 한다. PC가 없어도 로컬 NVS에 저장되어 재부팅 후 복원되어야 한다.
- UI는 등록한 폰의 이름, 페어링 여부, 연결됨/재연결 대기/부재/오류를 보여 준다. 주변 BT 목록·주소 선택·별칭 추가 UI는 제거한다.
- PC UI는 보드의 상태와 지원 기능을 표시한다. 폰을 PC에 페어링시키거나 PC로 폰을 탐지하지 않는다. 첫 폰 등록·번호 비교는 보드 LCD와 폰의 기본 설정에서 수행한다.
- `presence_scan` 제어 요청과 `/api/presence-scan`, 스캔 상태/주변 목록 응답을 폐기한다. paired capability/schema를 구분하고 구형 PC·보드 조합에는 지원되지 않음을 명확히 표시한다. 구형 제어가 새 기능을 우회하지 않게 한다.
- 기존 사용량 서비스 UUID·프레이밍·ACK·PC heartbeat는 유지한다. PC 설정 revision 충돌 검사와 구형 메시지의 새 필드 생략 처리도 보존한다.
- 한국어·영어·일본어·중국어 간체·독일어를 함께 수정한다. 이름의 UTF-8 처리와 기존 폰트 지원은 유지한다.

## 7. 구현 단계와 단계별 종료 조건

### A. 현황 확인과 복구 준비

실제 포트·실행 중인 PC 패키지·이미지 해시·설정·본딩 수를 확인한다. 작업 중인 변경이 많으므로 기존 변경을 초기화하지 않는다. 현재 앱과 NVS를 로컬 백업하고 돌아갈 검증 이미지를 확보한다. 아래 9절을 출발점으로 쓴다.

### B. 최소한의 멀티 연결 구조와 폰 실증

연결 컨텍스트/역할 분리, 본딩 2개 보존, 대상별 번호 비교, 광고 재개, 연결 이벤트 계측을 우선 구현한다. 감지에 의한 화면 끄기는 비활성 상태로 둔다. 기존 PC 연결·데이터 권한을 먼저 검사한 뒤 Fold7 기본 설정으로 2절의 네 항목을 실물 시험한다.

**종료 조건:** PC 본딩이 보존되고 폰이 OS 기본 기능만으로 연결·잠금 유지·복귀 재연결을 수행한다는 로그와 사용자 확인이 있다. 미통과 시 전체 기능 완성을 주장하지 않고 이 단계에서 기술적 제약을 정리한다.

### C. paired 감지와 화면 제어

상태 모델·60초 타이머·PC 독립성·예약/터치 우선순위를 구현한다. 단위 검사 후 PC를 종료한 상태로 이탈·복귀를 확인한다.

### D. 광고 스캔 제거와 설정/UI 마이그레이션

## 11. 기술 근거와 남은 불확실성

- [ESP-IDF 5.5.3 ESP32-S3 복수 연결 안내](https://docs.espressif.com/projects/esp-idf/en/v5.5.3/esp32s3/api-guides/ble/ble-multiconnection-guide.html): 멀티 BLE 연결은 지원하지만 앱 메모리와 호스트/컨트롤러 설정에 따라 구성해야 한다.
- [Android GATT 연결 안내](https://developer.android.com/develop/connectivity/bluetooth/ble/connect-gatt-server): 앱의 GATT 연결/자동 연결 API를 설명한다. **폰 기본 설정이 임의의 GATT 보드에 같은 자동 연결을 제공한다는 보장은 아니다.**
- [Android BluetoothDevice API](https://developer.android.com/reference/android/bluetooth/BluetoothDevice): 본딩 생성과 GATT 연결은 별도 동작이다.
- [AOSP CachedBluetoothDevice 참고 구현](https://android.googlesource.com/platform/frameworks/base/+/dd7fc9f1a3abadcf27ef928841847a9a2ce9f7c6/packages/SettingsLib/src/com/android/settingslib/bluetooth/CachedBluetoothDevice.java): `startPairing()`은 `createBond()`를 호출하고, 별도 `connectDevice()`는 인식한 profile 목록이 비어 있으면 연결을 시작하지 않고 반환한다. 일반 GATT 본딩만으로 OS의 지속 연결이 생긴다고 가정하기 어렵다는 근거다. 이는 참고 구현에서의 추론이며 Fold7/Samsung 구현을 직접 확인한 결과가 아니다. B단계 실물 게이트는 유지한다.

따라서 이 계획의 가장 큰 기술적 불확실성은 보드의 멀티 연결 가능 여부가 아니라 **Fold7 기본 OS가 추가 앱 없이 사용할 연결/재연결 경로**다. 이를 B단계에서 먼저 실증하고 결과에 따라 구현 범위를 판단한다.

광고 보완본 `20ef2472ad210ad410a494bf0fe9d1cfeab5e5d819ec81e2e9e2dd29950b9b60`의 업로드·플래시 검증과 업로드 전후 부트로더/파티션/NVS 동일 검사를 마쳤다. 기존 PC는 재페어링 없이 인증됐고 기존 중계가 새 런타임 통계를 수신한다. 직접 ACK 수신 증거는 아직 확보하지 않았다.

`tools/observe_ble_paired_advertising.mjs 22`는 설정에 저장된 보드 주소와 내부적으로 일치하는 광고만 집계한다. 2026-10-20 01:19:24–01:19:50 UTC 관찰에서 실제 광고 **22회**, 저장 본딩 열거 **1회**를 구분했고, Quotamon 이름과 기존 서비스 UUID 필터, RSSI -77~-56 dBm을 확인했다. 주소나 번호 비교 값은 기록하지 않는다. 이는 보드 광고 검증이며 PC를 통한 휴대폰 감지 기능이 아니다. 결과는 [실물 기록](ble-paired-trial-hardware.json)에 보존했다.

따라서 보드의 무선 광고 송출은 확인했지만, Fold7 목록에서 제외되는 정확한 내부 원인은 확정하지 못했다. 현재 일반 사용자 정의 GATT 경로가 OS 기본 설정 등록 시험을 통과하지 못했다는 결론으로 제한한다. 이름·광고 재개만 바꾸는 재업로드를 반복하거나 C/D/E를 진행하지 않는다.

### 후보와 판단

| 후보 | 판단 |

HOGP 선택 시 검토할 시험 범위는 다음과 같다. 아직 구현·업로드하지 않았다.

- 현재 NimBLE 호스트·역할·NVS를 유지하고 필요한 HID 서비스·리포트 맵·기기 정보를 구현한다. SDK의 `esp_hid`는 NimBLE 구현도 포함하지만 예제가 자동으로 볼륨 입력을 보내므로 그대로 적용하지 않는다.
- 키보드·마우스 용도를 제외한 소비자 제어 HID 리포트 맵을 검토하고, 키·마우스·미디어 입력 보고서를 자동 전송하지 않는다. 폰에서 입력 장치로 표시되는 점과 소프트 키보드·입력 동작에 영향이 없는지는 실제로 확인한다.
- 기존 PC 사용량 서비스와 본딩을 유지하며, PC/폰 GATT 권한·대상별 번호 비교·두 연결의 수명과 삭제는 계속 분리한다. Windows가 새 HID 서비스를 어떻게 처리하는지도 검사한다.
- PC 동시 사용량/ACK, 양쪽 번호 비교, 잠금 30분, 조작 없는 이탈/복귀 1회(16절의 사용자 변경 기준), PC 종료 상태를 다시 실증한다. 본딩 성공만으로 B를 통과 처리하지 않는다.

근거는 [Bluetooth SIG HOGP 정의](https://www.bluetooth.com/specifications/specs/hid-over-gatt-profile-hogp/), [AOSP 기본 설정의 프로파일별 연결](https://android.googlesource.com/platform/frameworks/base/+/dd7fc9f1a3abadcf27ef928841847a9a2ce9f7c6/packages/SettingsLib/src/com/android/settingslib/bluetooth/CachedBluetoothDevice.java), [AOSP 배터리 클라이언트](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/fe2c86b638cc53f84c242d7a7856d6a4bc7d699d/android/app/src/com/android/bluetooth/bas/BatteryService.java), [AOSP 프로파일 정책](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/619fafa41b7fe03ce7905422d966a59c68769f3d/android/app/src/com/android/bluetooth/btservice/PhonePolicy.java)이다. AOSP에서의 가능성은 사용자 Fold7/Samsung 구현의 성공 증거가 아니다.

## 14. 사용자 선택: HID 상호운용 시험 진행

사용자가 **“입력 장치로 등록하는 HID 시험 진행”**을 명시적으로 선택했다. 이 선택은 휴대폰에 HID 입력 장치로 등록해 잠금·자동 재연결과 입력 영향 여부를 검증하는 B단계 시험의 구현·적용을 포함한다. 같은 방향을 다시 승인받지 않는다. C/D/E의 실물 게이트는 그대로 유지한다.

시험본은 기존 PC 서비스를 먼저 등록해 속성 순서를 유지하고 HID(0x1812), Device Information(0x180A), Battery(0x180F) 서비스를 뒤에 추가한다. 기본 광고에는 이름·HID UUID·일반 HID Appearance(0x03C0), 스캔 응답에는 기존 PC 서비스 UUID를 싣는다. 키보드·마우스 컬렉션 없이 소비자 제어 입력 리포트(ID 1, 1바이트)를 정의하지만 알림 전송 경로는 PC 제어 characteristic에만 존재한다. 휴대폰의 리포트 읽기에는 모든 버튼이 해제된 0만 반환하며 Suspend 요청은 인증된 휴대폰 링크를 끊거나 부재로 간주하지 않는다.

HID companion 서비스도 시험 한계를 명시한다. 실제 배터리 계측이 없으므로 Battery Level 읽기는 애플리케이션 오류 0x80(측정 불가)을 반환하며 임의의 잔량을 표시하지 않는다. PnP ID는 다른 업체 제품의 ID를 사칭하지 않는 미할당 시험 ID(FFFF:0001)다. 따라서 이 시험본에 Bluetooth 프로파일 적합성 인증을 주장하지 않는다. 기본 설정 검색·양쪽 번호 비교·잠금 유지·복귀와 PC 회귀를 실제로 통과하는지를 검사한다.

HID 시험본은 SHA-256 `2a4d9adfd7f560b541dbe6979eff4a9b5006bdc56e22d5ef0647803081d50ba1`, 4,972,816바이트다. 펌웨어·네이티브 빌드, 실제 전송 소스의 HID 리포트·권한·Suspend·자동 입력 알림 미발생을 포함한 CTest 7개와 5개 언어 LCD 조작 검사를 통과했다. 사용자의 다운로드 모드 준비 후 COM5에서 이전 `20ef…` 앱·NVS를 `.local/board-ble-paired-trial-20261020-112421/`에 백업·해시 검증하고 새 앱 영역 업로드·플래시 검증을 마쳤다. 업로드 전후 부트로더·파티션·NVS는 동일했다. HID 이미지의 부팅·폰 기본 설정 등록과 연결 동작은 별도 실물 게이트이며 아직 통과하지 않았다.

Fold7 기본 설정 페어링·인증·HID 구독과 사용자 기본 키보드/입력 정상 확인을 마쳤다. 휴대폰 잠금 시험은 11:37:21 KST 시작, 최소 종료 12:07:21이며 사용자 확인은 12:08 이후다. 보드 재부팅·펌웨어 변경 없이 계속 관찰 중이다.

## 16. 사용자 변경: 실제 이탈·복귀 시험 1회로 충족

사용자가 “계획서를 수정해서 1번으로 충족하자. 생각보다 거리가 너무 멀어”라고 명시했다. 실제 BLE 연결 범위 밖으로 이동하는 부담을 반영해, 실제 거리 이탈·복귀 반복 기준을 기존 5회에서 **1회**로 변경한다. 이미 수행한 1회로 이 항목을 충족하며 추가 4회를 요청하지 않는다.

## 17. C단계 구현 시작: paired 상태와 LCD 제어

사용자가 다음 구현을 명시적으로 요청했다. 7절 B 종료 조건인 기존 PC 본딩·사용량/ACK 보존, Fold7 기본 설정 등록·인증, 잠금 30분 유지, 사용자 변경 기준에 따른 실제 거리 복귀 1회는 로그와 사용자 확인을 모두 확보했으므로 **B 연결 게이트를 통과**한 것으로 정리한다. 앞서 남겨 둔 PC 완전 종료 상태의 독립 동작은 7절 C에 정한 구현 후 실물 검증이며, C 구현 자체를 막는 선행 조건으로 해석하지 않는다. PC 종료 상태·화면 끄기/켜기 등 미검증 결과는 유지한다.

C 소스는 인증된 폰 링크 기반 상태 모델과 연결 해제 시각부터 60초 유예, 재연결 취소, 라디오 오류 시 감지로 화면을 끄지 않기와 복구 후 새 유예, 대상 삭제/변경, 예약 우선·터치 5분 점등을 구현 중이다. 보드 NVS의 `paired_on`과 LCD 스위치로 감지를 제어하며 구형 PC 광고 설정은 새 감지를 켜거나 끄지 못한다. 검증된 HID/PC GATT 속성 순서는 유지한다. 현재 보드에는 여전히 B 이미지가 실행 중이며, C는 빌드·모의 검사 및 별도 산출물 준비 후 업로드한다. 광고 필드/API 전면 제거와 PC 상태 UI 마이그레이션은 D단계로 남긴다.

### C 시험본 앱 업로드·읽기 검증 완료

## 18. C 실물 결과와 D 설정/UI 전환

이전 C 실물 시험 이미지는 `f43a9658caf76c0d3d8cd200ae05bfa3892af09a67ec15f40fa34fcf6aea6be7`이다. 사용자는 사용량 자동 복구, BT 끄기 후 약 60초 LCD 꺼짐, BT 켜기 후 자동 연결·화면 켜짐, 폰 부재 중 터치 5분 점등 후 꺼짐을 모두 정상으로 확인했다. 실제 로그의 해제→꺼짐은 60,088ms, 인증→켜짐은 66ms, 터치 점등 구간은 300,044ms다. [C 실물 기록](ble-paired-presence-hardware.json)을 따른다. C 직접 ACK 수신, 실물 예약 우선순위, 로컬 감지 스위치 재부팅 복원, PC 완전 종료 상태는 아직 미검증이다. 이미 통과한 실제 거리 복귀 1회를 다시 5회로 늘리지 않는다.

D 소스는 주변 검색·주소/별칭 설정·검색 API·목록 UI를 제거했다. 공통 UTF-8 처리는 `bluetooth_name.h`로 분리했다. PC 설정 검증은 폐기 필드를 버리면서 계정·예약·언어·밝기와 revision을 보존한다. 보드의 구형 `quotamon-ui/presence` blob은 main DRAM 작업에서 제거하며 `paired_on`·보안 역할·NimBLE 키는 유지한다.

기존 B/C 폰 역할에는 보드가 무작위 16바이트 표시 ID를 추가한다. 이 값은 PC에 32자리 소문자 hex `peer_id`로 전달하며 MAC/IRK/LTK를 포함하지 않고 접근 권한을 주지 않는다. 저장 ID는 재연결·재부팅에 유지하고 폰 삭제 시 함께 지운다. 폰의 원격 이름은 OS에서 읽지 않으므로 현재 표시는 5개 언어의 일반명 ‘등록된 휴대폰’이다. 이름/주소로 감지하지 않는다.

새 PC는 schema2 미지원 보드를 명확히 안내하고 사용량 서비스는 유지한다. 새 보드는 구형 스냅샷의 광고 필드를 무시하고 구형 제어에는 `unsupported_control`을 반환한다. 보드 검색용 Windows 스캔은 기존 PC 연결 기능이므로 유지한다. 읽기 전용 PC 상태 화면과 LCD 등록/삭제/스위치를 5개 언어로 검증한다.

D 산출물은 `dist/Quotamon-BLE-paired-migration-firmware`, PC는 `dist/Quotamon-Paired-Portable`로 분리하며 [D 빌드 기록](ble-paired-migration-build.json)을 사용한다. B/C 이미지·실물 근거를 덮어쓰지 않는다. 소프트웨어 검사 후 새 BOOT/RESET 준비를 받아 현재 C 앱/NVS를 새 백업하고 `tools/flash_ble_paired_trial.py --stage D --port COM5 --baseline-build docs/ble-paired-presence-build.json`으로 앱만 업로드·읽기 검증한다. PC 적용도 기존 경로·자동 실행·유효 설정과 본딩을 보존한다. 아직 D 실물 성공을 주장하지 않는다.

### D 핵심 실물 확인과 남은 E 항목

사용자는 D 전원 재연결 후 사용량과 폰 자동 연결 정상 복구를 확인했다. 실제 설치 중계에서 스냅샷 ACK 1건을 확인했고, 기존 트레이 중계에서도 사용량 5개 표시가 복원됐다. 새 PC 화면의 ‘등록된 휴대폰 / 휴대폰 연결됨 / 휴대폰 감지 켜짐’ 스크린샷은 schema2 상태와 표시 ID 마이그레이션이 수신됐다는 근거다. 일반명 표시는 정상이다.

임시 단일-client 진단 중계 종료 후 트레이로 전환하면서 PC 링크가 t130199ms에 해제돼 사용량 대기 화면이 잠시 표시됐다. PC가 t147239ms에 재인증했고 자동으로 사용량을 복구했다. 사용자의 이 현상 보고와 진단 전환 시각이 일치함을 보존했다. 보드 재업로드나 본딩 초기화는 하지 않았다. 그 뒤 원래 트레이를 유지한 75초 표본 6개에서 BLE와 사용량5가 유지됐다. CPU 평균은 6.55~7.96%, LVGL 7.199~8.798fps, 가용 PSRAM 1,973,524바이트, 내부 RAM 108,167~108,195바이트였다. 장시간 누수 검증으로 확대하지 않는다.

예약 우선순위 실물 시험은 사용자가 ‘지금 시험 어려움’으로 답해 수행하지 않았다. 시험용 임시 예약은 적용하지 않았으며 실제 원래 설정인 **예약 켜짐·18:00~07:00·revision7**을 그대로 보존했다. 앞서 복원 시각23:00을 제시한 것은 기본값 가정 오류였고 사용자에게 실제 저장값으로 정정했다. 폐기 필드 네 개를 제외한 설치 설정이 이전과 의미상 정확히 일치함을 재확인했다. 자체 진단 캡처는 종료하고 설치 트레이 중계와 자동 실행은 유지했다.

D 구현·적용과 핵심 상태 표시는 확인했으나 E 전체 통과는 아니다. 남은 실물 항목은 예약 우선순위, 로컬 감지 스위치 재부팅 복원, PC 완전 종료 상태의 독립 화면 제어, 폰 재부팅 후 재연결, 선택 삭제/재등록 및 더 긴 안정성이다. 사용자가 시험 가능한 때 이어가며, 현재 검증 이미지를 이유 없이 다시 플래시하지 않는다. [D 실물 기록](ble-paired-migration-hardware.json)에 미검증을 유지한다.
